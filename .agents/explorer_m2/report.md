## 1. Executive Summary

This report evaluates Milestone M2 (Requirement R2: Credit-Control Escalation & Statutory Calculation Engine) across the Invoice Rescue codebase.

### Core Verdict
The foundational mathematical and state machine components (`statutory-interest.ts`, `escalation.ts`, and `gemini.ts`) are implemented and pass all existing test suites (354 passing tests, 0 TypeScript errors, clean dry-run worker build). However, critical architectural, functional, and prompt-generation discrepancies were identified that directly impact production correctness and compliance with the R2 acceptance criteria.

Most critically:
1. **Placeholder Defect in Live Prompts**: In `backend/src/index.ts:839-851`, `runOverdueDetection` fails to pass `clientBusinessName: inv.company_name` to `buildChasePrompt`. Consequently, every automated chase draft prompt generated by Gemini falls back to the literal placeholder `[Client Business Name]` in the locked sign-off block!
2. **Missing `chase-runner.ts` Abstraction**: `backend/src/lib/chase-runner.ts` does not exist. Overdue detection and draft staging are currently implemented as an un-exported private function inside the 1,366-line `backend/src/index.ts`.
3. **Cadence Gap on Late Ingestion**: `runOverdueDetection` uses `nextStepDue(daysOverdue, history)` which evaluates overdue days against static cadence thresholds `[1, 8, 15, 22]`. If an invoice is imported 15+ days overdue, it will trigger Step 1 on day 1, Step 2 on day 2, and Step 3 on day 3, violating the requirement that subsequent stages must wait 7+ days after the prior chase.
4. **Draft Concurrency / Multiple Unreviewed Drafts**: `runOverdueDetection` does not verify whether an unreviewed draft (`status = 'draft'`) already exists before queuing another stage draft.
5. **Missing Automated Terminal Transition**: When an invoice exceeds Stage 4 + 7 days without payment, `invoices.status` is never transitioned to `'escalated'` (the DB equivalent of `handed_back`); it remains `'overdue'` and is scanned indefinitely on every cron run.

### 3.2 `backend/src/lib/escalation.ts`
- **Location**: `backend/src/lib/escalation.ts` (Lines 1–86)
- **Functions & Constants**:
  - `CADENCE_DAYS = [1, 8, 15, 22]`
  - `STEP_LABELS = ["", "reminder", "follow-up", "firm notice", "final notice"]`
  - `nextStepDue(daysOverdue: number, history: ChaseHistoryRow[]): number | null`:
    ```typescript
    export function nextStepDue(daysOverdue: number, history: ChaseHistoryRow[]): number | null {
      const lastStep = history.reduce((max, h) => Math.max(max, h.step), 0);
      const nextStep = lastStep + 1;
      if (nextStep > CADENCE_DAYS.length) return null;
      return daysOverdue >= CADENCE_DAYS[nextStep - 1] ? nextStep : null;
    }
    ```
  - `advanceEscalationStage(state: InvoiceEscalationState, today: Date): EscalationDecision`:
    Calculates stage transitions respecting `daysSinceChase >= 7` and returns descriptive nextAction strings.
- **Evaluation**:
  - `advanceEscalationStage` contains the accurate interval logic (`DAYS_SINCE_CHASE_FOR_STAGE2 = 7`), but it is **orphaned** (never called in `backend/src/index.ts` or anywhere in runtime code).
  - `nextStepDue` is called by `index.ts`, but it only accepts `history: ChaseHistoryRow[]` where `ChaseHistoryRow` only has `step: number`. It has no knowledge of timestamps (`sent_at`), so it cannot enforce 7-day intervals after late sends or late imports.

  ```typescript
  async function runOverdueDetection(env: Env): Promise<void> {
  ```

- **Critical Defects in this Routine**:
  1. **Missing `clientBusinessName`**: Line 839 calls `buildChasePrompt` without `clientBusinessName: inv.company_name`. In production, Gemini receives `[Client Business Name]` in the prompt and sign-off block!
  2. **No Guard for Pending Drafts**: If `chase_log` already has a row for `invoice_id` with `status = 'draft'`, `nextStepDue` evaluates based on whatever steps exist, or can draft an invalid next step while the operator has not yet approved or skipped the current draft.

## 5. Detailed Gap Analysis & Recommendations

### Gap 1: Prompt Construction Omission (`clientBusinessName`)
- **Severity**: HIGH
- **Location**: `backend/src/index.ts:839-851`
- **Root Cause**: `buildChasePrompt` expects `clientBusinessName?: string`. In `index.ts`, `c.company_name` is selected as `inv.company_name`, but omitted from the argument object.
- **Fix**: Add `clientBusinessName: inv.company_name` to the `buildChasePrompt` parameters.

### Gap 2: Architectural Modularization (`chase-runner.ts`)
- **Severity**: MEDIUM
- **Location**: Expected at `backend/src/lib/chase-runner.ts`
- **Root Cause**: `runOverdueDetection` is an un-exported private function in `backend/src/index.ts`.
- **Fix**: Extract `runOverdueDetection` into a dedicated service class or function in `backend/src/lib/chase-runner.ts`. Export `runOverdueDetection(env: Env, now?: Date): Promise<ChaseRunResult>`. Update `backend/src/index.ts` to import and invoke it.

### Gap 3: Enforcing 7-Day Spacing Between Successive Chases
- **Severity**: MEDIUM-HIGH
- **Location**: `backend/src/lib/escalation.ts` & `backend/src/index.ts:830-835`
- **Root Cause**: `nextStepDue` only checks `inv.days_overdue >= CADENCE_DAYS[nextStep - 1]`.
- **Fix**: Query the latest `sent_at` timestamp from `chase_log WHERE invoice_id = ?1 AND status = 'sent'`. For steps > 1, require `daysSinceLastChase >= 7` in addition to minimum overdue days.

### Gap 4: Guard Against Multiple Pending Drafts
- **Severity**: MEDIUM
- **Location**: `backend/src/index.ts:829-835`
- **Root Cause**: An invoice with an existing pending draft (`status = 'draft'`) can have subsequent drafts generated if overdue days increase.
- **Fix**: Check `SELECT id FROM chase_log WHERE invoice_id = ?1 AND status = 'draft'`. If a draft is already pending review, skip generating another draft until the existing one is either approved or skipped.

### Gap 5: Automated Hand-Back / Terminal Escalation
- **Severity**: MEDIUM
- **Location**: `backend/src/index.ts:835-836`
- **Root Cause**: When step sequence is exhausted (Stage 4 was sent 7+ days ago), the loop simply continues.
- **Fix**: If an invoice has completed step 4, and `daysSinceStep4 >= 7`, transition `UPDATE invoices SET status = 'escalated' WHERE id = ?1` and trigger operator notification (`env.NOTIFY`) to deliver the collection pack to the client.

### Gap 6: Schema Constraint vs Domain Type Naming
- **Severity**: LOW-MEDIUM
- **Location**: `backend/src/types/core.ts:1` vs `backend/db/migrations/0003_add_check_constraints.sql:68`
- **Root Cause**: `core.ts` uses `'handed_back'`, while the database `invoices.status` CHECK constraint uses `'escalated'`.
- **Fix**: Document that in the D1 database layer, the handed back state is represented by `'escalated'`. Ensure repository methods and queries map `'handed_back'` $\leftrightarrow$ `'escalated'` cleanly.

## 7. Conclusion

The M2 statutory calculation engine (`statutory-interest.ts`) is 100% sound, precise, and statutory-compliant with UK legislation. The escalation cadence definitions (`escalation.ts`) and prompt instructions (`gemini.ts`) are well-designed. However, the runtime orchestration currently in `backend/src/index.ts` requires extraction into `backend/src/lib/chase-runner.ts`, prompt argument fixing (`clientBusinessName`), pending draft gating, and terminal state escalation automation. All test suites pass 100% today, and these refinements will complete Milestone M2 to elite engineering standards.
