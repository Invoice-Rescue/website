## 3. Findings & Code Inspection

### [Major] Finding 1: Review Queue Delay Flaw — `sent_at` Priority Over `reviewed_at`

- **Location**: `backend/src/lib/chase-runner.ts:148, 192` & `backend/src/index.ts:558`
- **Issue Description**:
  In `0003_add_check_constraints.sql`, the `chase_log` table defines:
  ```sql
  sent_at TEXT NOT NULL DEFAULT (datetime('now'))
  ```
  When a draft is generated by `runOverdueDetection` (`chase-runner.ts:230-234`), `sent_at` is populated immediately with the draft creation timestamp.
  When an operator approves a draft in the review queue (`backend/src/index.ts:558`), `handleChaseApprove` updates `status = 'sent'` and `reviewed_at = datetime('now')`, but does NOT update `sent_at`.
  In `chase-runner.ts:192`, the spacing check evaluates:
  ```typescript
  const lastChaseDate = parseDate(lastChase.sent_at || lastChase.reviewed_at || "");
  ```
  Because `lastChase.sent_at` is always populated by default, `lastChase.sent_at` is always selected, and `reviewed_at` is never evaluated!
  Similarly, for Stage 4 exhaustion (`chase-runner.ts:148`):
  ```typescript
  const stage4Date = parseDate(stage4Sent.sent_at);
  ```
  `reviewed_at` is not even considered.
- **Blast Radius**:
  If an operator takes 5 days to approve Stage 1 in the review queue, the debtor receives the email on Day 5. However, `lastChaseDate` records Day 0. On Day 7 (only 2 days after the debtor received the reminder!), `diffDays` evaluates to 7, and Stage 2 is drafted prematurely. For Stage 4, an invoice could be marked escalated and handed back before the debtor has had 7 days to respond to the final notice.
- **Suggested Fix**:
  1. In `chase-runner.ts:192`, prioritize `reviewed_at` over `sent_at`:
     ```typescript
     const lastChaseDate = parseDate(lastChase.reviewed_at || lastChase.sent_at || "");
     ```
  2. In `chase-runner.ts:148`, use:
     ```typescript
     const stage4Date = parseDate(stage4Sent.reviewed_at || stage4Sent.sent_at || "");
     ```
  3. In `backend/src/index.ts:558`, also update `sent_at`:
     ```sql
     UPDATE chase_log SET status = 'sent', sent_at = datetime('now'), reviewed_at = datetime('now'), ...
     ```

### [Minor] Finding 2: `parseDate` Handling of ISO Timezone Offsets

- **Location**: `backend/src/lib/chase-runner.ts:29-40`
- **Issue Description**:
  `parseDate` attempts to ensure UTC timestamps by appending `"Z"`:
  ```typescript
  if (trimmed.includes("T")) {
    return new Date(trimmed.endsWith("Z") ? trimmed : trimmed + "Z");
  }
  ```
  If an ISO date string already contains a numerical timezone offset (e.g. `2026-09-16T12:00:00+01:00`), `trimmed.endsWith("Z")` is false, resulting in `2026-09-16T12:00:00+01:00Z`, which is an `Invalid Date` in V8/Node.js (`d.getTime()` returns `NaN`).
- **Blast Radius**:
  In current production, timestamps come from SQLite (`YYYY-MM-DD HH:MM:SS`) or `now.toISOString()` (ends in `Z`), so normal execution paths are unaffected. However, if dates with timezone offsets are injected via CSV imports or external webhooks, `parseDate` will fail silently or yield `NaN`.
- **Suggested Fix**:
  Use regex to detect timezone offsets (`[+-]\d{2}:?\d{2}$`) or pass directly to `new Date(trimmed)` when `"T"` is present.
